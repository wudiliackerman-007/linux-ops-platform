### Q1. 负载高和 CPU 使用率高是一回事吗？（本项目）

**考点**：`load average` 统计的是可运行和不可中断进程数，CPU 使用率是时间占比，两者不能划等号。

**回答**：  
我不会只看 `top` 里的 CPU 百分比。`load average` 是 1、5、15 分钟三个值，统计 R 状态和 D 状态进程；这台机器 4 核，5 分钟 load 到 8 就是每核 2 个任务，所以我把 `HostHighLoad` 定成 `node_load5 > 8` 持续 10 分钟。  
CPU 高但 load 不高，可能是单线程短时突发；load 高但 CPU 不高，我会先怀疑 IO 等待，用 `iostat -x 1` 看 `%iowait`，再用 `ps -eo state,pid,cmd | awk '$1=="D"'` 找 D 状态进程。  
项目里的 CPU 演练是 4 个 bash 死循环打满 4 核，`top -o %CPU` 能看到，5 分钟后 `HostHighCPU` 触发；如果只是 load 高、CPU 不高，就不能直接加 CPU。  
最后要回到业务：看 P95 延迟和错误率有没有一起变坏，单纯一个 load 数字不构成结论。

**追问**：
- 4 核 load 8 一定有问题吗？—— 不一定，要看持续时间和业务延迟；短时压测到 8 可以接受，持续 10 分钟且延迟上升才处理。
- load 高但 CPU 低，你先看什么？—— 先看 `iostat -x 1` 的 `%iowait` 和 D 状态进程，再排磁盘、NFS 或网络存储。

### Q2. 内存没满，为什么进程会被 OOM Kill？（本项目）

**考点**：Linux 看的是可回收内存和 overcommit，不是 `free` 里那个“已用”数字；OOM Killer 会在内存压力大时挑进程杀。

**回答**：  
我会先看 `free -m` 的 `available`，而不是只看 `used`；page cache 可回收，`available` 才接近应用能拿到的内存。  
然后查内核日志：`dmesg -T | grep -i -E 'oom|killed process'`，或者 `journalctl -k --since '1 hour ago'`，能看到被杀进程的 RSS 和触发时的内存情况。  
这台机器 6GB 内存、2GB swap，我配了 `vm.swappiness=10`，swap 只做兜底；但 swap 不是内存，真到 OOM 还是要看谁在涨。用 `ps aux --sort=-rss | head` 找大进程，再看它是不是随时间线性增长。  
项目里用 `increase(node_vmstat_oom_kill[10m]) > 0` 做 `HostOOMKill` 告警，发生一次就报 critical，因为内核已经开始杀进程了，不能等到业务全挂。  
止血可以先重启异常进程或加内存，但根因要看代码/配置有没有泄漏，不能只把 `oom_score_adj` 调低。

**追问**：
- 为什么 `free` 显示内存快满但系统还正常？—— 大部分是 page cache，可回收；看 `available` 和 `%memused`，不要被 `used` 吓到。
- OOM 和 swap 用满是什么关系？—— swap 用满会加剧内存回收压力，但是否 OOM 取决于当时是否有可回收页和 overcommit 策略，不是简单的等号。

### Q3. 文件句柄耗尽怎么定位？（本项目）

**考点**：Linux 一切皆文件，句柄泄漏会表现为 `Too many open files`、新连接建不上，但 CPU/内存可能都正常。

**回答**：  
我先看进程自己的限制：`cat /proc/<pid>/limits | grep 'open files'`，再看系统级 `fs.file-max`；项目里 limits 配的是 65535，`node_filefd_allocated / node_filefd_maximum > 85%` 会触发 `HostFileDescriptorsHigh`。  
定位用 `lsof -p <pid> | wc -l` 看总数，`lsof -p <pid> | awk '{print $5}' | sort | uniq -c` 看是 socket、日志还是普通文件；也可以 `ls /proc/<pid>/fd | wc -l`。  
如果是 socket 泄漏，配合 `ss -s`、`ss -tanp | grep <pid>` 看连接状态；如果是日志文件，检查 logrotate 和应用有没有反复打开不关。  
止血可以临时 `ulimit -n` 或重启进程，但根因要回到代码：连接池有没有归还、文件有没有 `close()`、异常分支有没有漏掉清理。  
我不会一上来把限制调到 100 万，那只是把问题往后拖，最后可能连系统都进不去。

**追问**：
- 句柄数和连接数是一回事吗？—— 不完全是，socket 连接会占句柄，但日志、管道、epoll 也占；要看 `lsof` 的类型分布。
- 为什么重启能好？—— 重启释放了泄漏的句柄，但没有修复代码；所以要保留现场，抓 `lsof` 和堆栈再重启。

### Q4. 进程状态 D、Z、R、S 分别说明什么？

**考点**：`ps` 的 STAT 第一位是进程状态，D 和 Z 是排障时最需要警惕的两个。

**回答**：  
R 是正在运行或可运行，S 是可中断睡眠，通常在等事件，T 是暂停，Z 是僵尸。  
D 是不可中断睡眠，常见于等磁盘 IO、NFS 或内核锁；这时候 `kill -9` 也没用，进程要等内核操作返回，所以我先看 `ps -eo stat,pid,ppid,cmd | grep '^D'` 和 `iostat -x 1`。  
Z 是子进程已经退出但父进程没 `wait()`，本身不占 CPU，占的是 PID 表项；找到父进程，修 `wait` 逻辑或重启父进程。  
项目里 MySQL 磁盘压力大时可能看到 D 状态，我的处理顺序是：先确认是哪个设备/挂载点，再看 `dmesg` 有没有 IO 错误，最后才考虑重启服务。  
`ps` 只能看瞬间，反复采样用 `pidstat -p ALL 1` 或 `top` 观察状态变化。

**追问**：
- D 状态进程能杀吗？—— 不能强制杀，信号要等内核路径返回；先解决底层 IO 或重启相关服务。
- 僵尸进程会占内存吗？—— 基本不占，但会占 PID；大量僵尸说明父进程回收逻辑有问题。

### Q5. systemd 服务起不来，按什么顺序排查？（本项目）

**考点**：systemd 排障要按“单元定义 → 启动命令 → 运行环境 → 端口/依赖 → 日志”顺序，不要盲目重启。

**回答**：  
先 `systemctl status opslink -l` 看退出码和最后几行，再 `journalctl -u opslink -n 100 --no-pager` 看完整报错；如果是配置问题，`systemctl cat opslink` 看 `ExecStart`、`WorkingDirectory`、`EnvironmentFile` 是否指向真实路径。  
这个项目的应用跑在 `/opt/ops-platform/current/app`，`current` 是软链；如果发布后起不来，我会 `readlink -f current` 看指向哪个 release，再检查 venv 里的 gunicorn、`/etc/ops-platform/app.env` 权限和端口占用。  
端口用 `ss -lntp | grep 8000`，依赖用 `systemctl status mysql redis-server`，配置语法用 `nginx -t` 这类工具先校验，不要直接 reload。  
如果确认是新版本代码问题，先用 `rollback.sh` 切回上一版止血，再保留日志慢慢定位；重启不是根因分析。  
最后才考虑 `systemctl daemon-reload`，因为改了 unit 文件不 reload，systemd 还可能用旧定义。

**追问**：
- `systemctl restart` 和 `reload` 怎么选？—— 改 unit/二进制用 restart；Nginx 这类支持平滑 reload 的优先 reload，避免断连接。
- 服务一直 `activating` 怎么办？—— 看 `journalctl` 和 `systemctl show -p TimeoutStartUSec`，多半是启动命令前台阻塞或探针没通过。

### Q6. TIME_WAIT 很多需要处理吗？

**考点**：TIME_WAIT 是主动关闭方正常的 2MSL 状态，数量多不等于故障，关键看端口是否耗尽、是否影响新建连接。

**回答**：  
先确认数量：`ss -tan state time-wait | wc -l`，再看 `ss -s` 的汇总；如果是 Nginx 主动关大量短连接，TIME_WAIT 多是正常的。  
只有当地址/端口组合快耗尽、出现 `Cannot assign requested address`，或者连接建立明显变慢，才需要处理。  
项目里我开了 `net.ipv4.tcp_tw_reuse = 1` 和 `tcp_fin_timeout = 15`，Nginx 到后端的 upstream 配了 `keepalive 32`，目的就是减少短连接，而不是靠调内核参数硬扛。  
我不会开 `tcp_tw_recycle`，它在 NAT 环境下会带来很隐蔽的问题，而且新内核已经移除了。  
如果是应用侧短连接太多，优先改连接池/长连接；内核参数只是辅助。

**追问**：
- TIME_WAIT 和 CLOSE_WAIT 哪个更危险？—— CLOSE_WAIT 多通常说明应用没关连接，是代码/连接池问题；TIME_WAIT 是正常回收过程。
- 为什么是 2MSL？—— 保证最后一个 ACK 能到达，并让旧连接的重复报文在网络中消失，避免污染新连接。

### Q7. 502、503、504 分别是谁的问题？（本项目）

**考点**：三个码都发生在代理链路，但责任点不同：502 是上游不可用/响应非法，503 是服务明确不可用，504 是等上游超时。

**回答**：  
502 是 Nginx 连不上上游，或者上游返回了 Nginx 不认识的响应；这个项目里 `systemctl stop opslink` 后，Nginx 就会返回 502，因为 8000 端口没人监听。  
503 是服务明确告诉你“现在不可用”，比如应用连不上 MySQL 时返回 503，或者 Nginx 自己因为限流/维护返回；项目的 `/health/ready` 在 MySQL 不可用时就是 503。  
504 是 Nginx 等上游超过 `proxy_read_timeout`，项目里配的是 30 秒；如果网络延迟或应用卡死超过 30 秒，就会看到 504。  
排查先 `curl -kI https://127.0.0.1/...` 看码，再看 `/var/log/nginx/opslink_error.log` 的 upstream 信息，同时 `journalctl -u opslink` 和 `ss -lntp | grep 8000` 确认应用在不在。  
不要只看 Nginx 日志就重启 Nginx，502 很多时候根因在应用或数据库。

**追问**：
- 502 和 504 怎么快速区分？—— 502 通常马上返回，错误日志是 connection refused/invalid response；504 会等一段时间，日志是 upstream timed out。
- 503 一定是应用返回的吗？—— 不一定，Nginx 自己、负载均衡、应用都能返回；看响应头和 body，再对照 upstream 日志。

### Q8. DNS 解析失败怎么排查？

**考点**：DNS 问题要区分“解析失败”“解析到错 IP”“解析慢”，排查顺序是本地配置 → DNS 服务器 → 网络可达性。

**回答**：  
先 `getent hosts example.com` 和 `dig +short example.com`，前者走系统 NSS，后者直接查 DNS；如果 `dig` 通、`getent` 不通，要看 `/etc/nsswitch.conf` 和 `/etc/hosts`。  
再看 `/etc/resolv.conf` 或 `resolvectl status`，确认 DNS 服务器地址；可以换一个公共 DNS 做对比，比如 `dig @223.5.5.5 example.com`。  
如果解析正常但访问失败，问题可能不在 DNS，用 `curl -v` 看卡在解析还是连接；`ping` 只能证明 ICMP，不能证明 443 通。  
这个项目在 VMware NAT 里，我会先确认虚拟机网络模式、网关和 DNS 是不是跟着 NAT 走；换网络后 `/etc/resolv.conf` 可能被改。  
解析慢还要看 `dig` 的 `Query time`，以及有没有配置多个不可达的 DNS 导致超时重试。

**追问**：
- `ping` 通但网站打不开，可能是什么？—— 可能 DNS 正常但 443 被挡、证书错误、代理配置错误，或者应用层返回错误。
- 为什么要用 `getent`？—— 它模拟应用的真实解析路径，能反映 `/etc/hosts`、NSS 和 DNS 的综合结果。

### Q9. 端口不通，从哪几层查？防火墙怎么确认？

**考点**：端口不通要按“进程有没有监听 → 监听地址对不对 → 防火墙 → 路由/NAT → 抓包”逐层排除。

**回答**：  
先在服务器上 `ss -lntp | grep <端口>`，确认进程在听；再看监听地址是 `127.0.0.1` 还是 `0.0.0.0`，这个项目应用只监听 `127.0.0.1:8000`，外部本来就不该通，只能走 Nginx 443。  
本机 `curl -vk https://127.0.0.1/health/live` 通、外部不通，优先查防火墙：`ufw status numbered`，看 22/80/443 有没有放行；项目只开放 22、80、443、3000、9090、9093，8000/3306/6379/9100 都不对外。  
再查路由和 NAT：`ip route`、`ip -4 addr`，VMware NAT 要看虚拟网络编辑器和主机防火墙；需要时 `tcpdump -i any -nn port 443` 看包有没有到网卡。  
如果包到了但没回，可能是 Nginx 没监听、证书/协议不匹配或后端 502；如果包没到，问题在主机网络/防火墙/NAT。  
改防火墙用 `ufw allow 443/tcp`，删规则用 `ufw delete <编号>`，改完 `ufw status` 复核，不要直接 `ufw disable` 图省事。

**追问**：
- `ss` 和 `netstat` 怎么选？—— 优先 `ss`，更快且默认信息更全；老系统没有 `ss` 再用 `netstat -lntp`。
- 防火墙开着但本机 curl 通、外部不通，优先查什么？—— 查监听地址和云主机/VMware 的安全组/NAT 端口映射，再看主机防火墙。

### Q10. 磁盘满了怎么排查和救急？（本项目）

**考点**：磁盘满要先区分数据、日志、inode 和“已删除但被进程占用”的文件，救急要可回退，不能上来就 `rm -rf`。

**回答**：  
先 `df -h` 看哪个挂载点满，再 `df -i` 看是不是 inode 满；项目里根分区和 `/data` 是分开看的，`/data` 满和根分区满处理方式不一样。  
定位大目录用 `du -sh /* 2>/dev/null | sort -h`，再逐层下钻；日志重点看 `/var/log`、`journalctl --disk-usage`，项目给 journald 设了 `SystemMaxUse=500M`，但还是可能被应用日志或旧 release 占满。  
如果 `df` 显示满但 `du` 对不上，查 `lsof +L1`，可能是进程还占着已删除的文件；这种要重启对应进程才能释放。  
救急优先清可再生的东西：旧日志、旧 release、临时文件、过期备份；不要删 `/var/lib/mysql`、当前 release 和正在写的文件。  
项目里 `HostDiskUsageHigh` 是根分区 >80% 持续 10 分钟，`HostDiskWillFull` 用 `predict_linear(...[6h], 4*3600) < 0` 预测 4 小时内写满；演练脚本只填 `/data`，到点自动清理。  
磁盘满会让 MySQL 写失败、应用 5xx，所以恢复后还要检查数据库和备份是否完整。

**追问**：
- `df` 满但 `du` 不大，为什么？—— 可能有被删除但仍被进程打开的文件，或者挂载点被覆盖；用 `lsof +L1` 和 `mount` 排查。
- 能不能直接删 MySQL 的 binlog？—— 可以按保留策略用 `PURGE BINARY LOGS`，不要直接 `rm`，否则复制和恢复会出问题。

### Q11. MySQL 慢查询怎么定位？（本项目）

**考点**：慢查询要靠慢日志 + `EXPLAIN` + 业务 SQL 上下文，不是只看 `SHOW PROCESSLIST` 一瞬间。

**回答**：  
项目里开了 `slow_query_log=ON`，`long_query_time=1`，`min_examined_row_limit=100`，慢日志在 `/var/log/mysql/slow.log`；先 `mysqldumpslow -s t /var/log/mysql/slow.log | head` 按总耗时排序，找到最值得优化的 SQL。  
然后对具体 SQL 做 `EXPLAIN`，重点看 `type`、`key`、`rows`、`Extra`；如果出现 `ALL`、`Using filesort`、`Using temporary`，要结合表结构和数据量判断。  
这个项目的短码查询走 `code` 上的唯一索引，正常应该是 `const/eq_ref`；如果查询条件对字段做函数、隐式类型转换或用 `%abc` 前缀匹配，就可能全表扫。  
优化优先加合适的联合索引、改写 SQL、减少返回列；不要盲目加索引，写多读少的表加太多索引会拖慢写入。  
监控侧用 `rate(mysql_global_status_slow_queries[5m]) > 0.1` 持续 10 分钟触发 `MySQLSlowQueries`，提醒我去看日志，而不是等用户投诉。

**追问**：
- `EXPLAIN` 里 `rows` 很小但还是很慢，为什么？—— 可能回表、排序、锁等待或网络/磁盘慢，结合 `EXPLAIN ANALYZE`、`SHOW PROFILE` 和 `iostat` 看。
- 慢查询日志会不会影响性能？—— 会有一点开销，`long_query_time` 不要设得太低，`log_queries_not_using_indexes` 在库大时也容易刷日志。

### Q12. MySQL 连接数被打满怎么办？（本项目）

**考点**：连接数满要区分真并发、连接泄漏、慢 SQL 占连接和连接池配置，先止血再定位。

**回答**：  
先看现场：`SHOW STATUS LIKE 'Threads_connected';`、`SHOW VARIABLES LIKE 'max_connections';`、`SHOW PROCESSLIST;`，重点找大量 `Sleep` 或长时间 `Query` 的连接。  
这个项目 6GB 内存按 `MEM_MB/16` 推算，`max_connections` 封顶 200；应用连接池只有 8 个连接，正常不应该打满，打满通常是泄漏、慢查询占住或外部工具连太多。  
如果是慢 SQL 占连接，先 `KILL` 掉明显异常的长事务/长查询止血，再优化 SQL；如果是连接池没归还，查代码里 `finally` 有没有 `put` 回池。  
临时可以小幅调大 `max_connections`，但要同时看内存和 `thread_stack`，不能无脑加；项目用 `MySQLHighConnections > 80%` 持续 5 分钟告警。  
长期要做连接池上限、`wait_timeout`、慢查询治理和监控，不能靠重启 MySQL。

**追问**：
- `Threads_connected` 和 `Threads_running` 有什么区别？—— 前者是已建立的连接，后者是正在执行的查询；连接多但 running 少，更像空闲连接/泄漏。
- 为什么连接池不是越大越好？—— 每个连接占内存和数据库线程资源，过大反而增加上下文切换和锁竞争。

### Q13. 什么时候索引会失效？怎么验证？

**考点**：索引失效常见于对列做函数、隐式类型转换、前导模糊匹配、OR 条件和不合适的联合索引顺序。

**回答**：  
我会先用 `EXPLAIN` 看执行计划，重点看 `type` 是不是 `ALL`、`key` 是不是 `NULL`、`rows` 是否接近全表；必要时用 `EXPLAIN ANALYZE` 看实际耗时。  
常见失效：`WHERE DATE(created_at)=...` 对列做函数、字符串列用数字比较触发隐式转换、`LIKE '%abc'` 前导模糊、`OR` 连接了无索引列、联合索引不满足最左前缀。  
这个项目的短码是等值查询，`code` 上有唯一索引，正常应该走索引；如果查询里对 `code` 做 `LOWER()` 或类型不一致，就可能退化。  
验证不能只看 `possible_keys`，要看最终选的 `key` 和 `rows`；数据分布也会影响优化器选择，统计信息过期时先 `ANALYZE TABLE`。  
加索引后要回归写入性能和磁盘占用，不是索引越多越好。

**追问**：
- 联合索引 `(a,b,c)`，只查 `b` 能走索引吗？—— 一般不能，除非有覆盖索引/索引跳跃扫描等特殊情况；优先按最左前缀设计。
- 为什么 `LIKE '%abc'` 不走索引？—— B+ 树按前缀有序，前导通配符无法定位起点，只能扫。

### Q14. 怎么证明备份真的能恢复？（本项目）

**考点**：备份的完成标志不是“文件生成了”，而是“校验通过 + 能恢复 + 数据对得上”。

**回答**：  
项目的备份脚本不是 `mysqldump` 完就结束：它用 `--single-transaction --quick --routines --triggers --events` 导出，gzip 后做 `gzip -t`，再检查文件里有没有 `Dump completed`，并且文件大小至少 1KB。  
任一校验失败就把状态写成 0，退出码非 0，同时把 `ops_backup_last_success_timestamp_seconds`、`ops_backup_last_size_bytes` 写到 node_exporter 的 textfile；`BackupStale > 48h` 和 `BackupSizeAnomaly` 会告警。  
更关键的是每周日 `restore_test.sh` 把最新备份真正恢复到临时库 `opslink_restore_check`，比对 `links` 表行数，成功后再删临时库；这才叫“备份可用”。  
保留策略是 7 天日备 + 4 周周备；当前 RPO 最多 24 小时，RTO 对这个小库是分钟级。  
不足也要说：备份和数据库在同一台机器、没有异地、没有 binlog 时间点恢复，这些是下一步要补的。

**追问**：
- `--single-transaction` 为什么能不锁表？—— 它用 InnoDB 一致性快照读，导出期间不阻塞 DML，但只对事务引擎有效。
- 备份文件多大算正常？—— 没有绝对标准，要和历史大小、表行数对比；突然变小或小于 1KB 都要报警。

### Q15. MySQL 主从复制的原理是什么？延迟怎么看？

**考点**：主从靠 binlog 传输和 relay log 重放，延迟要看复制线程和 `Seconds_Behind`，不能只看 `SHOW SLAVE STATUS` 的一行。

**回答**：  
主库把变更写进 binlog；从库的 IO 线程连主库，把 binlog 拉到本地 relay log；SQL 线程再重放 relay log，这就是异步复制的基本链路。  
看状态用 `SHOW REPLICA STATUS\G`（老版本是 `SHOW SLAVE STATUS\G`），重点看 `Replica_IO_Running`、`Replica_SQL_Running` 是否都是 `Yes`，以及 `Seconds_Behind_Source`（老版本叫 `Seconds_Behind_Master`）。  
延迟常见原因：从库单线程重放跟不上、大事务、从库磁盘/CPU 瓶颈、网络抖动；可以开并行复制、拆大事务、加索引。  
还要注意主从数据不一致：`pt-table-checksum` 这类工具可以校验，但项目里没做，不能假装做过。  
这个项目是单机，没有主从；面试里我会把它当“下一步的高可用方案”讲，而不是说已经落地。

**追问**：
- 主从延迟会导致什么业务问题？—— 读写分离时读到旧数据，刚下单查不到；要按业务做“读主”或延迟阈值降级。
- 半同步复制和异步复制的区别？—— 半同步等至少一个从库确认收到 binlog 再提交，数据更安全但延迟更高；异步不等待。

### Q16. 缓存穿透、击穿、雪崩有什么区别？（本项目）

**考点**：穿透是查不存在的数据，击穿是热点 key 过期瞬间并发回源，雪崩是大量 key 同时失效或缓存整体不可用。

**回答**：  
穿透是请求的 key 在缓存和数据库都不存在，每次都打到 DB；常用空值缓存（短 TTL）、布隆过滤器、参数校验。  
击穿是某个热点 key 过期，瞬间大量请求同时回源；常用互斥锁/单飞、逻辑过期、热点永不过期。  
雪崩是大量 key 同一时间过期，或者 Redis 整体挂了，DB 压力瞬间上去；常用 TTL 加随机抖动、多级缓存、限流降级。  
这个项目的 TTL 固定 3600 秒，没做随机抖动，也没做布隆过滤器和互斥重建；它做的是“Redis 不可用时降级直连 MySQL”，并通过 `opslink_dependency_up{dependency="redis"}` 暴露状态。  
所以我会诚实说：项目覆盖了“缓存整体不可用”的降级，但穿透/击穿的完整防护还没做，这是明确的改进项。

**追问**：
- 空值缓存会不会占内存？—— 会，所以 TTL 要短，并限制 key 数量；布隆过滤器更省空间但有误判。
- 降级直连 MySQL 会不会把 DB 打挂？—— 会，所以还要限流、连接池上限和容量评估；降级不是免费午餐。

### Q17. Redis 内存满了会怎样？

**考点**：`maxmemory` 触发后行为由 `maxmemory-policy` 决定，是淘汰、报错还是只读，取决于策略。

**回答**：  
项目里配了 `maxmemory 256mb` 和 `maxmemory-policy allkeys-lru`，内存到上限后会按 LRU 淘汰任意 key，写请求通常还能继续，但可能把热 key 淘汰掉，导致命中率下降、回源变多。  
如果是 `noeviction`，写命令会直接报 `OOM command not allowed`，读还能用；这适合不能丢数据的场景，但不适合纯缓存。  
排查用 `INFO memory` 看 `used_memory`、`maxmemory`、`evicted_keys`，再看 `INFO stats` 的命中率；项目里缓存命中率低于 70% 持续 15 分钟会触发 `AppCacheHitRateLow`。  
项目还禁用了 `FLUSHALL` 和 `CONFIG`，避免误操作和远程改配置；改配置走配置文件 + 重启/滚动，不在线上随手 `CONFIG SET`。  
如果经常淘汰，先看是不是 key 太大、TTL 太长或内存给少了，不要只调大 `maxmemory` 把机器吃爆。

**追问**：
- `allkeys-lru` 和 `volatile-lru` 的区别？—— 前者从所有 key 淘汰，后者只淘汰设置了过期时间的 key；没有 TTL 的 key 在 volatile 策略下不会被淘汰。
- Redis 的 LRU 是精确的吗？—— 是近似 LRU，采样若干 key 选最久未使用的，成本和精度之间取平衡。

### Q18. Redis 挂了，业务会怎样？（本项目）

**考点**：缓存是加速层，不是唯一数据源；降级要自动、可见、可恢复，不能静默失败。

**回答**：  
项目的 `RedisCache` 连接超时和读写超时都设了 1 秒，连不上或抛异常就 `reset()`，读请求直接回源 MySQL，所以短链跳转仍然可用，只是 DB 压力变大、P95 可能上升。  
`/health/ready` 不会因为 Redis 挂而返回 503，因为 Redis 只是缓存，不是“不就绪”的必要条件；但 `opslink_dependency_up{dependency="redis"}` 会变成 0，`AppCacheDegraded` 持续 10 分钟发 warning。  
这个设计的关键是“降级必须可见”：如果不暴露这个指标，业务表面上正常，DB 却在独自扛流量，迟早出更大的问题。  
恢复后下一次请求会重新尝试连接 Redis，不需要重启应用；但缓存是冷的，命中率会先低后高，要看 `opslink_cache_hits_total`。  
演练时我会跑 `05_redis_down.sh 660`，多留一分钟覆盖 `for: 10m`，确认短链仍 302、`AppCacheDegraded` 出现、Redis 恢复后指标回 1。

**追问**：
- 降级后数据库扛不住怎么办？—— 要限流、连接池上限、只读降级或排队；项目目前只做了降级，没有做 DB 过载保护，这是不足。
- 为什么 `/health/ready` 不检查 Redis？—— 就绪探针应该反映“能不能提供核心服务”，Redis 挂了核心读仍可用；如果业务强依赖缓存，才应该把它算成就绪条件。

### Q19. Nginx 反向代理和限流怎么配？（本项目）

**考点**：反代要配 upstream、超时和转发头；限流要选对 key、速率、burst 和拒绝码。

**回答**：  
项目用 `upstream opslink_backend { server 127.0.0.1:8000; keepalive 32; }`，`proxy_pass` 到 upstream，并带 `Host`、`X-Real-IP`、`X-Forwarded-For`、`X-Forwarded-Proto`，超时是 connect 5s、read 30s。  
限流在 `http` 层定义 `limit_req_zone $binary_remote_addr zone=api_limit:10m rate=20r/s;`，在 `/api/` 里 `limit_req zone=api_limit burst=40 nodelay;`，超过就返回 429。  
`burst=40 nodelay` 的意思是允许瞬时 40 个排队请求立即处理，超过才拒绝；如果不加 `nodelay`，突发会被延迟处理，用户会感觉慢。  
配置改完先 `nginx -t`，再 `systemctl reload nginx`；验证用 `curl -kI https://127.0.0.1/...` 和并发请求看 429。  
另外 `/metrics` 只允许 127.0.0.1 和内网段，`stub_status` 只在 127.0.0.1:8081，不给公网看。

**追问**：
- 为什么用 `$binary_remote_addr` 而不是 `$remote_addr`？—— 二进制更省内存，限流 key 更紧凑；效果等价。
- `limit_req` 和 `limit_conn` 的区别？—— 前者限请求速率，后者限并发连接数；项目两个都用了。

### Q20. Nginx 499 是什么？怎么排查？

**考点**：499 是 Nginx 自定义状态码，表示客户端在服务端返回响应前主动关闭了连接，不一定是应用错误。

**回答**：  
499 常见于客户端超时、用户取消、上游太慢导致客户端先断开；Nginx 只是记录“我还没写完，客户端走了”。  
项目访问日志是 JSON，包含 `status`、`request_time`、`upstream_time`，我会用 `jq` 筛 `status==499`，对比 `request_time` 和 `upstream_time`，判断是客户端等不及还是后端太慢。  
如果 499 集中在某个接口且 `upstream_time` 很高，先查应用/MySQL/Redis 的 P95；如果 `upstream_time` 不高但 `request_time` 高，可能是客户端网络或代理链路。  
不要直接把 499 当 5xx 告警，它更多是客户端行为；但如果量突然上升，要结合业务和上游延迟一起看。  
项目里 `AppHighLatencyP95 > 0.5s` 持续 5 分钟会告警，能提前发现“慢到客户端放弃”的趋势。

**追问**：
- 499 和 502 怎么区分？—— 499 是客户端先断，502 是 Nginx 连不上/收不到上游有效响应；看日志里的 upstream 字段。
- 499 多了要不要调大超时？—— 先确认是谁的超时；盲目调大 Nginx 超时可能只是让资源占用更久。

### Q21. Prometheus 为什么用拉模型？（本项目）

**考点**：拉模型由 Prometheus 主动抓取，天然带 `up` 健康信号，目标发现和抓取节奏集中在服务端，适合长期运行的指标。

**回答**：  
Prometheus 每隔 `scrape_interval`（项目是 15 秒）主动请求目标的 `/metrics`，抓不到就把 `up` 置 0；这本身就是最基础的可用性检测。  
拉模型下，目标只需要暴露 HTTP 接口，不用知道 Prometheus 在哪，也不用装 agent 推数据；项目里 node_exporter、mysqld_exporter、nginx-prometheus-exporter 都只监听 127.0.0.1，由本机 Prometheus 拉。  
`up{job="opslink"} == 0` 就是 `AppDown` 的依据；`TargetDown` 再做一层兜底，任何 exporter 挂了都能发现。  
短生命周期任务不适合拉，可以用 Pushgateway；但项目里的定时备份不是靠 Pushgateway，而是脚本写 textfile，让 node_exporter 暴露。  
拉模型的代价是目标要能被 Prometheus 访问，网络策略要放行；这也是为什么 exporter 只绑本地，减少攻击面。

**追问**：
- 拉模型怎么发现新实例？—— 用 static_configs、文件发现或服务发现；项目是单机，直接写静态目标。
- Prometheus 自己挂了怎么办？—— 需要外部监控/第二套 Prometheus 或至少告警到外部；项目目前是单点，这是不足。

### Q22. Counter、Gauge、Histogram、Summary 怎么选？

**考点**：Counter 只增，Gauge 可增可减，Histogram 在客户端分桶、服务端算分位数，Summary 在客户端算分位数。

**回答**：  
Counter 适合累计请求数、错误数，比如 `opslink_http_requests_total`、`opslink_links_created_total`；查速率要用 `rate()`，不能直接看总量。  
Gauge 适合当前值，比如 `opslink_dependency_up`、`node_load5`、`node_memory_MemAvailable_bytes`；可以直接看瞬时值或做 `predict_linear`。  
Histogram 适合延迟分布，项目里的 `opslink_http_request_duration_seconds` 就是 Histogram，服务端用 `histogram_quantile(0.95, ...)` 算 P95，桶的边界要按业务延迟设计。  
Summary 也在客户端算分位数，但不能跨实例聚合，成本也更高；这个项目主要用 Histogram，没有用 Summary。  
选型原则：能累计用 Counter，能直接测量用 Gauge，要分位数且要聚合用 Histogram，单实例且不想服务端算才考虑 Summary。  
label 也要克制：项目里的 path 用 `request.scope["route"].path`，不是真实 URL，否则每个短码都会多一条时间序列，几千条短链就能把 Prometheus 的基数和内存撑爆。

**追问**：
- Histogram 的 `_bucket`、`_sum`、`_count` 分别是什么？—— 累计桶计数、总和、样本数；`histogram_quantile` 主要用 bucket。
- 为什么 Counter 不能直接 `rate` 一个 Gauge？—— `rate` 假设单调递增，Gauge 会上下波动，结果没有意义。

### Q23. 写一条错误率和 P95 的 PromQL？

**考点**：错误率是 5xx 速率除以总速率，P95 用 Histogram 的 bucket 配合 `histogram_quantile`，窗口要覆盖至少几个抓取点。

**回答**：  
项目里的 5xx 错误率是：`sum(rate(opslink_http_requests_total{status=~"5.."}[5m])) / clamp_min(sum(rate(opslink_http_requests_total[5m])), 0.001) > 0.05`。  
`clamp_min` 是防止分母为 0；5 分钟窗口在 15 秒抓取下有 20 个点，足够算速率，又不会太迟钝。  
P95 是：`histogram_quantile(0.95, sum by (le) (rate(opslink_http_request_duration_seconds_bucket[5m]))) > 0.5`。  
`sum by (le)` 先把所有实例/方法的桶合并，再算分位数；如果没有 `by (le)`，`histogram_quantile` 无法正确聚合。  
这两条都配了 `for: 5m`，避免瞬时抖动；错误率是 critical，P95 是 warning，因为延迟高不一定要立刻叫醒人。

**追问**：
- 为什么分母要 `clamp_min`？—— 没流量时分母为 0，会产生 NaN/Inf，告警结果不稳定。
- P95 为什么不用平均值？—— 平均值会被少数极慢请求掩盖，分位数更能反映用户体验。

### Q24. 告警太多怎么办？（本项目）

**考点**：降噪不是把告警关掉，而是让每条告警可行动、有优先级、能合并、能抑制。

**回答**：  
项目里 3 个规则文件共 28 条规则，先按 `severity` 分 critical/warning；critical 的 `group_wait` 是 10 秒、`repeat_interval` 1 小时，warning 是 2 分钟和 6 小时，避免同一批告警刷屏。  
条件都带 `for`，比如 `HostHighCPU` 要持续 5 分钟、`HostDiskUsageHigh` 要 10 分钟；抖一下就响的告警最后一定会被人关掉。  
Alertmanager 用 `group_by: ["alertname","instance","severity"]` 合并同类告警；`HostDown` 抑制同实例的 warning，`AppDown` 抑制 `AppHighErrorRate`，因为主机/应用都不可达时，衍生告警没有额外信息。  
再进一步是删掉不可行动的规则、维护窗口静默、把“通知”和“工单”分开；项目目前只发 webhook，没有值班轮换和真实渠道。  
我的原则是：每条告警都要能回答“我现在该做什么”，回答不了就不应该发。

**追问**：
- `for` 和 `group_wait` 有什么区别？—— `for` 是 Prometheus 判断条件持续多久才 firing，`group_wait` 是 Alertmanager 收到后等多久合并发送。
- 抑制规则会不会漏掉真问题？—— 会，所以只在因果关系明确时用，并且 `equal` 要限定实例，不能全局抑制。

### Q25. textfile collector 解决什么问题？（本项目）

**考点**：让脚本把业务/运维结果写成 Prometheus 文本格式，由 node_exporter 统一暴露，不用为每个脚本写 exporter。

**回答**：  
项目的备份、巡检、恢复演练都是 shell 脚本，不可能各自起一个 HTTP exporter；它们把结果写到 `/var/lib/node_exporter/textfile_collector/*.prom`，node_exporter 启动时带 `--collector.textfile.directory` 就能抓。  
写入用 `mktemp` 创建临时文件再 `mv` 原子替换，避免 Prometheus 抓到半个文件；这是 textfile 最容易踩的坑。  
项目暴露了 `ops_backup_last_success_timestamp_seconds`、`ops_backup_last_size_bytes`、`ops_healthcheck_ok`、`ops_restore_test_ok` 等指标，告警规则直接查这些值。  
好处是脚本简单、可测试、失败也能留下指标；坏处是依赖 node_exporter，且 textfile 里的指标没有类型校验，写错格式会静默丢。  
所以我会在脚本里固定 HELP/TYPE，并在部署后 `curl 127.0.0.1:9100/metrics | grep ops_` 验证。

**追问**：
- 为什么不用 Pushgateway？—— 定时脚本可以用 Pushgateway，但 textfile 更简单，指标和主机绑定，适合单机项目；Pushgateway 适合短任务和跨主机。
- textfile 文件权限要注意什么？—— node_exporter 要能读，通常 644；写入方要有目录权限，原子替换避免半文件。

### Q26. 你的发布为什么能快速回滚？（本项目）

**考点**：发布物不可变、当前版本用软链指向、回滚只切链接并重启，才能做到可预测的回退。

**回答**：  
每次发布都新建 `/opt/ops-platform/releases/<时间戳>`，代码和依赖准备好后，把 `current` 软链指过去，再 `systemctl restart opslink`；线上跑的是哪个 commit，看 `current/RELEASE` 就知道。  
回滚就是 `ln -sfn <上一个release> /opt/ops-platform/current` 再重启，项目封装成 `rollback.sh`，支持 `--list` 和指定版本；软链切换本身是瞬间的，重启需要几秒。  
因为旧版本目录还在，依赖也装在共享 venv 里，回滚不需要重新构建；保留最近 5 个版本，兼顾回滚和磁盘。  
发布脚本还会在切换后轮询 `/health/ready` 最多 30 秒，再做一次真实短链创建和 302 冒烟，失败自动切回上一版。  
所以“快”不是因为魔法，而是因为发布物不可变、切换动作小、验证自动化；它不是零停机，重启期间仍可能丢一两个请求。

**追问**：
- 为什么不用 `scp` 覆盖代码？—— 覆盖过程中进程可能读到半个文件，出问题也无法快速回到上一版，且不知道线上是哪个 commit。
- 软链切换后为什么要重启？—— 当前进程还持有旧代码/旧模块；重启才能让新版本生效，项目用 `TimeoutStopSec=35` 尽量优雅退出。

### Q27. 发布过程中怎么保证不中断、失败怎么办？（本项目）

**考点**：发布要做健康检查、业务冒烟、失败自动回滚，并尽量优雅停机；单机做不到真正零中断，要如实说。

**回答**：  
`release.sh` 的顺序是：记录当前版本 → `git fetch/reset` → 新建 release → 同步依赖 → 切 `current` → `systemctl restart opslink` → 30 秒内轮询 `/health/ready` → 创建短链并验证 302。  
systemd 配了 `KillSignal=SIGTERM`、`TimeoutStopSec=35`、`Restart=always`、`RestartSec=3`，让 gunicorn 有机会处理完在途请求，异常退出也能被拉起来。  
如果就绪探针或业务冒烟失败，脚本把 `current` 切回 `PREV`，再重启并检查健康；没有历史版本就明确报错，退出码非 0，不会假装成功。  
发布成功才写 `RELEASE` 文件，保留 5 个版本；失败时保留日志并用 `journalctl -u opslink -n 40` 输出现场。  
局限是单机重启仍有短暂不可用，Nginx 会返回 502；要做到真正无缝，需要多实例 + upstream 摘流/优雅下线，这是我下一步要补的。

**追问**：
- 健康检查通过就一定没问题吗？—— 不一定，所以项目加了真实业务冒烟；但冒烟也只覆盖一条主路径，不能替代完整回归。
- 发布失败后第一件事做什么？—— 先回滚止血，再保留日志和现场做根因分析，不要在故障中现场改代码。

### Q28. 灰度发布怎么做？你项目里做了吗？

**考点**：灰度是按比例/人群把流量切到新版本，观察错误率和延迟后再扩大；关键是可观测、可回退、流量可控。

**回答**：  
灰度的基本做法是新旧版本同时在线，用 Nginx 的 `split_clients` 按 IP/百分比分流，或者 upstream 权重、独立域名/端口，先放 5%～10% 流量，观察错误率、P95、日志和业务指标，再逐步加。  
必须有的配套是版本标识、回滚开关、对比看板和明确的停止条件；没有这些，灰度只是“随机让一部分用户帮你测试”。  
这个项目没有做真正的灰度，只有单版本 `releases/current` 和 `limit_req`；我会诚实说这是局限，不把“发布”包装成“灰度”。  
下一步可以在 Nginx 层做 `split_clients` + 两个 upstream，或者加一台应用机做小流量切分；但在单机上做灰度，资源隔离和观测都不够。  
面试官如果追问，我会把“知道概念”和“实际落地”分开说，这比硬编一个没做过的方案可信。

**追问**：
- 灰度和蓝绿的区别？—— 灰度按比例逐步放量，蓝绿是两套完整环境一次性切换；蓝绿回滚快，但资源翻倍。
- 灰度期间看什么指标？—— 错误率、P95/P99、关键业务成功率、日志异常量，和新旧版本对比。

### Q29. 最小权限在这个项目里落在哪些地方？（本项目）

**考点**：最小权限要落到账号、文件、网络监听、服务运行用户和 sudo 授权，不只是“别用 root”。

**回答**：  
系统层建了 `ops` 用户，`/etc/sudoers.d/90-ops-ops` 只放行 systemctl、journalctl、项目脚本、nginx 等少数命令，权限 440，用 `visudo -c` 校验，不是 `ALL=(ALL) ALL`。  
密钥文件 `/etc/ops-platform/platform.env` 是 600，应用环境文件 `app.env` 是 640（root:ops），`/root/.my.cnf` 和 `/etc/mysqld_exporter/.my.cnf` 都是 600，密码不进 Git、不上命令行。  
MySQL 只监听 127.0.0.1；应用账号 `opslink` 只有 `opslink.*` 的 SELECT/INSERT/UPDATE/DELETE，监控账号 `exporter` 只有 PROCESS、REPLICATION CLIENT。  
Redis 只监听 127.0.0.1，带 `requirepass`，禁用 `FLUSHALL`/`CONFIG`；所有 exporter 也只绑本地，减少攻击面。  
systemd 单元加了 `NoNewPrivileges=true`、`ProtectSystem=strict`、`PrivateTmp=true`、`ProtectHome=true`，应用即使被打穿，能改的东西也有限。  
SSH 只有在确认公钥可用后才关密码登录，`PermitRootLogin prohibit-password`，避免把自己锁在门外。

**追问**：
- 为什么密码文件是 600 而不是 644？—— 644 同组/其他用户可读，600 只有属主可读写；密钥文件不应让无关进程读到。
- sudoers 放行脚本目录有什么风险？—— 如果目录可被普通用户写，就能提权；所以脚本目录必须 root 所有、权限受控，生产上还要更细粒度。

### Q30. on-call 接到告警怎么处理？复盘和 SLO 呢？（本项目）

**考点**：on-call 是先确认影响面、止血、沟通、再根因；复盘对事不对人；SLO 用可量化的目标约束可靠性投入。

**回答**：  
接到告警先确认是不是真故障：看 `9090/alerts`、Grafana 和 `healthcheck.sh`，判断影响面是单机、单服务还是全站，再决定优先级；不要一上来重启所有服务。  
止血优先：能回滚就 `rollback.sh`，能重启单实例就重启，能切流量就切；同时在看板/群里同步“已发现、正在处理、影响范围”，避免重复排查。  
根因分析看时间线、最近变更、日志和指标，把“触发原因”和“根本原因”分开；恢复后补监控/告警/脚本，防止同样问题再来。  
复盘对事不对人：写清楚时间线、影响、根因、处置、改进项、负责人和截止时间；不写“某人粗心”，写“哪个检查缺失、哪个流程要补”。  
SLO 是把可靠性量化，比如月度 99.9% 可用性，错误预算约 43 分钟；项目没有正式 SLO，但用探针、告警和巡检做了近似，面试时我会说清楚这是实验环境，不是生产 SLO。  
这个项目告警只到 webhook + 日志，没有值班轮换和电话通知，这是局限；下一步可以接企业微信/钉钉并做分级。

**追问**：
- 故障中先止损还是先找根因？—— 先止损，保留现场；根因分析放在恢复之后，除非止血动作会破坏关键证据。
- SLO 和 SLA 的区别？—— SLO 是内部目标，SLA 是对外承诺；SLA 通常比 SLO 宽松，并带赔偿条款。

## 追加 3 题：部署与可复现（面试官最爱在这条线上追问）

### Q31. 你的部署脚本怎么保证可以重复执行（幂等）？

**考点**：幂等不是「重跑不报错」，而是「重跑之后状态和之前一致」。

**回答**：  
脚本里所有「有副作用」的动作都先判断再执行：目录用 `mkdir -p`、系统用户用 `id -u || useradd`、装包用 `dpkg -s` 判断、写配置前先比对内容（不同才写）、密码只在文件不存在时生成（`get_or_create_secret`），所以重跑不会把线上密码改掉。  
验证方式不是看退出码，而是对比重跑前后的状态：`/etc/ops-platform/platform.env` 与 `app.env` 的 sha256 一致、8 个单元仍 active、7/7 抓取目标 up、28 条规则没重复加载、release 目录仍保留 5 个。实测在已装好的机器上重跑 `all_in_one.sh`：**43 秒**完成（首次 12 分钟），两个密钥文件哈希完全没变。

**追问**：
- 幂等和「重启服务」冲突吗？—— 不冲突，但要区分「幂等」和「无副作用」：重启是幂等操作（结果一样），只是有中断；所以发布脚本重启前会做就绪检查，失败切回上一版。
- 状态在哪？—— 全部落在文件里（systemd 单元、`/etc/ops-platform`、`/data`），没有「存在内存里的期望状态」，所以脚本只要对着文件判断就行。

### Q32. 你怎么保证别人拿到你的仓库能装起来？

**考点**：这是「Demo 能跑」和「可交付」的分水岭。

**回答**：  
三个层次：第一，配置里不写死我这台机器的值（IP 用 `primary_ip()` 检测、密钥随机生成、路径全用 `common.sh` 里的常量）；第二，必须换机器验证——我在**两台全新虚拟机**上从零装过，另外机器被误重装一次也算一遍：分别 7 分 09 秒、8 分 47 秒装完，6/6 阶段 OK、0 条 `[ERROR]`、装完巡检 20/20。  
第三，还要验证「clone 下来就能用」：Windows 上提交的 `.sh` 默认是 644，别人 clone 到 Linux 后 `./deploy/all_in_one.sh` 会 `Permission denied`，我用 `git update-index --chmod=+x` 全部改成 755。然后真的 `git clone` 到临时目录（`/tmp/clonetest/linux-ops-platform`）做两件事：先静态检查（21 个脚本 `bash -n` 全过、promtool 三份规则 OK、pytest 6 passed、文档引用的 17 个路径 0 缺失），**再就在 clone 目录里跑一键部署**：285 秒装完、`ALLINONE_RC=0`、0 条 `[ERROR]`、8 个单元 active、7/7 目标 up、短链 302、巡检 20/20。  
只做静态检查不够——`bash -n` 过了不代表能装，所以最后那一步必须真跑一次安装。
这两遍干净机器还暴露了两个只有新机才有的 bug（`sysctl` 读不存在的键导致 `set -e` 静默退出；装完还没到备份时间导致巡检 1/20 失败），都是修在脚本里而不是修在那台机器上。

**追问**：
- 怎么发现「在我机器上是好的」？—— 只有换机器，没有别的办法；所以我把它做成了固定流程。
- 装不上时你怎么定位？—— 看 `docs/10` 的卡点表：先看日志里有没有 `[ERROR]`，再按症状（apt 卡住/502/证书/No data）查对应命令。

### Q33. 安装脚本怎么保证出错时不会「静默继续」或者「静默退出」？

**考点**：`set -euo pipefail` 的双面性——它能阻止错误被忽略，也会让脚本毫无提示地死掉。

**回答**：  
主体用 `set -euo pipefail`：未定义变量、管道中间失败、命令非 0 都立刻停，避免「明明失败了还继续往下装」。  
但 `set -e` 有个坑：`cur="$(sysctl -n 某个不存在的键 | norm)"` 里 `sysctl` 返回 255，管道失败直接把脚本干掉，**没有任何输出**——我就在干净机器上踩到了，看起来像脚本卡死。所以对「允许失败」的读取一律加 `|| true` 并显式处理空值，`trap` 里打印失败行号。  
另一面是别把错误藏起来：脚本统一用 `log_ok/log_warn/log_error`，判断标准写进文档——**`[ERROR]` 才是错，`[WARN]`/`[SKIP]` 可以放过**；关键步骤后立刻做真实验证（起没起来要 `curl` 一次、探针要真的返回 200），而不是「命令执行了就当成功」。

**追问**：
- `set -e` 在 `if`/`||` 里为什么失效？—— 处于条件上下文时不触发；这正是要显式检查返回值的原因。
- 为什么不写 `set -x`？—— 日志会被命令刷满；调试时单独 `bash -x` 跑一次。
