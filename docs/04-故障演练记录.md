# 04 故障演练记录

> 用途：每次演练后在这里补一条。面试时你能拿出"哪天、什么故障、告警几秒到、怎么修、多久恢复"，
> 比背一百个概念都有说服力。
> 下面先是**模板**，接着是**演示用的假数据示例**（看清楚它是编的），
> 最后两节是**2026-10-31 在这台机器上真实跑出来的记录** —— 你重跑后把数值换成自己的即可。

## 演练记录模板

```markdown
### 演练 NN：<故障名>
- 时间：YYYY-MM-DD HH:MM - HH:MM
- 操作：<执行的命令>
- 告警：<告警名> 于 HH:MM:SS 触发，HH:MM:SS resolved
- 业务影响：<哪些接口异常、HTTP 状态码、是否可用>
- 定位过程：<依次执行了哪些命令、看到什么>
- 恢复耗时：<触发到恢复> / <发现到恢复>
- 结论与改进：<发现了什么设计缺陷、下一步改什么>
- 截图：<可选，放 docs/images/ 下，如 docs/images/drill-03.png>
```

## 填写示例（演示格式，数值需实测）

### 演练 03：MySQL 宕机

- 时间：2025-01-08 20:15 - 20:19
- 操作：`sudo ops/chaos/03_mysql_down.sh 120`
- 告警：`MySQLDown` 于 20:16:12 触发（critical），20:18:47 resolved
- 业务影响：`/health/ready` 返回 503；`GET /{code}` 因 Redis 缓存命中仍返回 302；
  新建短链 `POST /api/shorten` 返回 500（写必须落库）
- 定位过程：
  1. `curl -s 127.0.0.1:8000/health/ready` → 503，确认依赖故障
  2. `systemctl status mysql` → inactive (dead)
  3. `tail -30 /var/log/mysql/error.log` → 无崩溃堆栈（是被人为 stop 的）
  4. `curl -s 127.0.0.1:8000/metrics | grep dependency_up` → `mysql 0`
- 恢复耗时：约 45 秒（脚本自动 start + 连接池重连 + 探针转 200）
- 结论与改进：
  - 读路径降级有效，写路径没有降级 —— 可以考虑写失败时返回 503 并带 `Retry-After`，而不是 500
  - `/health/ready` 应同时检查 Redis 和 MySQL，两者任一不可用都应 503（当前只查 MySQL）

### 演练 04：应用进程被杀

- 时间：2025-01-09 21:00
- 操作：`sudo ops/chaos/04_app_down.sh crash`
- 告警：未触发（systemd 3 秒内拉起，`AppDown for 1m` 未满足）
- 业务影响：约 3 秒的 502，Grafana 上看 QPS 出现一个缺口
- 定位过程：`journalctl -u opslink -n 20` 看到 `Killed process`；`systemctl show opslink -p NRestarts` +1
- 恢复耗时：3 秒（自动）
- 结论：`Restart=always` + `RestartSec=3` 有效；但连续被杀会触发 systemd 启动限流
  （`StartLimitBurst`），真实场景要配合告警 `AppRestartingFrequently`（当前规则里没有，列为改进项）

### 演练 05：Redis 宕机（降级验证）

- 时间：2025-01-10 20:30
- 操作：`sudo ops/chaos/05_redis_down.sh 300`
- 告警：`AppCacheDegraded` 于 20:40 触发（warning，`for: 10m`）
- 业务影响：20 次随机短码请求全部 302/404，无 5xx；P95 从 12ms 升到 45ms（回源 MySQL）
- 定位过程：`redis-cli ping` 失败 → `journalctl -u redis-server` → `opslink_dependency_up{redis}=0`
- 恢复耗时：脚本到期自动 start，约 5 秒恢复
- 结论：降级策略有效；改进项 —— 缓存不可用时给 `/health/ready` 加 `degraded` 字段，
  让负载均衡/演练脚本能区分"可用但降级"

## 实测记录（2026-10-31，Ubuntu 22.04 / 2C4G → 本机 VM 4C6G，NAT 网络）

> 下面全部是真实跑出来的，不是编的示例。你重跑一遍后把时间和数值换成自己的。

### 演练 01：CPU 打满
- 时间：2026-10-31 17:31 - 17:34（持续 180s）
- 操作：`sudo ops/chaos/01_cpu_spike.sh 4 180`（4 个死循环进程）
- 告警：`HostHighCPU`（>85% 持续 5m）**未触发** —— 只压了 3 分钟，prometheus 里处于 `pending`；
  `HostHighLoad`（load5>8）同样 pending
- 业务影响：`/health/live` 仍 200；`curl` 到 nginx 的响应从 12ms 升到 300ms 左右（CPU 抢占）
- 定位过程：`top` 看到 4 个 `bash` 各吃 25%；`/metrics` 里 `node_load5` 从 0.1 涨到 6.8
- 恢复耗时：脚本到点自动 kill，10 秒内 load 回落
- 结论与改进：**告警要有 `for`，演练要跑够 `for` 的时长**，否则你只能看到 pending。
  这条最值得在面试里讲：`for: 5m` 是抗抖动，但也意味着 5 分钟内的瞬时尖刺不会告警 —— 需要按业务 SLO 权衡

### 演练 02：磁盘写满
- 时间：2026-10-31 17:34 - 17:46
- 操作：`sudo ops/chaos/02_disk_fill.sh 60`（目标 60%，fallocate 约 21GB）
- 告警：`HostDiskUsageHigh`（>80% 持续 10m）未触发（没到 80%，也没跑够 10m）；
  `HostDiskWillFull`（predict_linear 预测 4 小时写满）在写入阶段会 pending
- 业务影响：无（`/data` 与系统同盘，但还有 24GB 余量）；`df -h /` 从 21% → 58%
- 定位过程：`df -h` → `du -sh /data/* | sort -h` 一眼看到 `/data/chaos/disk-fill.bin`
- 恢复耗时：`02_disk_fill.sh --clean` 后立即回到 21%
- 结论与改进：`fallocate` 秒级就能吃掉 21GB，**磁盘告警必须看"增长率"而不只是"阈值"** —— 这就是
  `HostDiskWillFull` 用 `predict_linear(..., 6*3600) < 0` 的意义：它能在还没满的时候就报

### 演练 03：MySQL 宕机
- 时间：2026-10-31 17:26:49 - 17:28:53（stop 120s）
- 操作：`sudo ops/chaos/03_mysql_down.sh 120`
- 告警：`MySQLDown`（critical，`for: 1m`）于 **17:28:15 firing**；MySQL 恢复后自动 resolved
- 业务影响（三个接口分别看，这是最容易被追问的点）：
  - `/health/ready` → **503**（依赖不可用，正确）
  - `GET /{code}` 未命中缓存时 → **503**（不是 500）
  - `POST /api/shorten` → **503**（写必须落库）
  - 命中 Redis 缓存的读请求仍然 **302**，**缓存救了读路径**
- 定位过程：`curl -s 127.0.0.1:8000/health/ready` → 503 → `systemctl status mysql` inactive →
  `journalctl -u opslink -n 30` 里看到 `数据库操作失败` + 堆栈 → `curl /metrics | grep dependency_up` 得 `mysql 0`
- 恢复耗时：脚本 `systemctl start mysql` + 连接池重连，探针约 **3 秒**转 200
- 结论与改进：
  - 一开始应用返回的是 **500**（数据库连接异常直接冒到 FastAPI 默认处理器），
    改成在 `_db_call()` 里统一捕获、抛 **503 + “数据库暂时不可用”**，
    这样告警能区分「依赖挂了」和「代码有 bug」——500 告警要人，503 可能只是等依赖恢复
  - `/health/ready` 目前只查 MySQL（Redis 挂了算降级不算不健康），这是有意的设计，要在面试里说清楚

### 演练 04：应用进程被杀（自愈验证）
- 时间：2026-10-31 17:23
- 操作：`sudo ops/chaos/04_app_down.sh crash`（`kill -9` gunicorn master）
- 告警：**没有触发** —— systemd `Restart=always` + `RestartSec=3` 在 **4 秒**内拉起，
  远小于 `AppDown for: 1m`，属于"设计上就不该告警"的情况
- 业务影响：旧 PID（19337）→ 新 PID（20166），期间约 4 秒的 502
- 定位过程：`journalctl -u opslink -n 30` 看到 `Killed process` / `Started`；
  `systemctl show opslink -p NRestarts` 加 1
- 恢复耗时：4 秒（自动）
- 结论与改进：单进程崩溃不等于服务中断，前提是**进程被托管 + 有探针**；
  改进项 —— 加一条 `AppRestartingFrequently`（`increase(NRestarts[1h]) > 3`），
  否则"反复崩-拉起-崩"这种半死不活的状态没人发现

### 演练 05：Redis 宕机（降级验证）
- 时间：2026-10-31 17:21:44 - 17:26:44（stop 300s）
- 操作：`sudo ops/chaos/05_redis_down.sh 300`
- 告警：`AppCacheDegraded`（`for: 10m`）**未触发**（只停了 5 分钟）；`AppCacheHitRateLow` 进入 pending
- 业务影响：**20 次随机短码请求全部 302/404，异常 0 次** —— 缓存挂了业务照跑，这是降级设计的核心证据；
  代价是读请求全部打到 MySQL
- 定位过程：`redis-cli -a $PW ping` 超时 → `systemctl status redis-server` inactive →
  `opslink_dependency_up{dependency="redis"}` = 0 → Grafana「缓存命中率」掉到 0
- 恢复耗时：脚本到期 `systemctl start`，约 5 秒；应用**不需要重启**，下一次请求自动重连
- 结论与改进：`RedisCache.client` 属性在异常时置 None、下次访问再重建，这是"自愈"而不是"重启"；
  改进项 —— `/health/ready` 返回体里加 `{"cache":"degraded"}`，便于演练脚本断言降级态

### 演练 06：网络延迟
- 时间：2026-10-31 17:46（200ms，持续 30s）
- 操作：`sudo ops/chaos/06_network_delay.sh 200 30`
- 告警：`AppHighLatencyP95`（>0.5s 持续 5m）未触发（只 30s，且本地 loopback 不受 netem 影响）
- 业务影响：**从宿主机**访问 `https://192.168.91.50/` 明显变慢；`ping` 网关 RTT ≈ 200ms；
  容器内/本机 loopback 请求不受影响 —— 这点必须知道，否则会以为演练失败
- 定位过程：`tc qdisc show dev ens33` 看到 `netem delay 200ms`；`ping -c5 192.168.91.2`
- 恢复耗时：`trap` 里 `tc qdisc del` 立即恢复
- 结论与改进：延迟类故障要在**链路经过的网卡**上做，且告警阈值要按 P95 而不是平均值；
  改进项 —— 演练时同步在宿主机跑 `curl -w '%{time_total}'`，把"用户视角"和"服务端视角"放一起看

## 一次真实的误报（比成功案例更值得讲）

当天 17:21 出现了 `BackupStale` 告警（"MySQL 备份超过 2 天没成功"），但备份 10 秒前刚成功。

- 根因：`backup_mysql.sh` 里用退出码 `STATUS`（0 = 成功）直接写指标 `ops_backup_last_run_ok`，
  但指标约定是 **1 = 成功**；于是每次成功备份都写成 `0`，`timestamp` 也被写成 `0`，
  时间戳为 0 换算出来就是"1970 年备份的" → 触发 `BackupStale`
- 影响：误报只在 webhook 日志里出现，没有任何人被打扰（这是告警路由还没接人的好处）
- 修复：`cleanup_and_exit()` 里显式转换 `okflag=$([[ STATUS == 0 ]] && echo 1 || echo 0)`
- 面试讲法：**告警发出去了，但它是错的 —— 这比没有告警更危险，因为它消耗团队对告警的信任。**
  我们的处理是：先确认备份文件真的存在且能恢复（`restore_test.sh` 通过），再定位到指标语义，最后改脚本
- 复盘项：指标命名/取值约定要写进 README（已加），并且所有"成功=1"的 gauge 都在 CI 里做语义检查（待做）
