# 简历与面试表达

> 这份文档怎么用：简历部分直接挑一版改数字，口语稿要念出来录音，不要默读；所有表达都守住一条底线——只讲自己真跑过的东西。

## 一、简历上的三种写法

项目名建议写成：**linux-ops-platform | 单机 Linux 运维实践（个人项目）**。不要写成“生产级运维平台”，也不要写“高并发”，这个项目不是。

### 写法 A：一页简历精简版（4 条）

适合简历空间紧张、想突出“流程完整”的岗位。

```text
- 独立搭建 Ubuntu 22.04 单机运维环境：Nginx + FastAPI/gunicorn + MySQL 8 + Redis，
  6 个部署脚本支持从裸机一键重建，应用由 systemd 托管。
- 设计 releases/<时间戳> + current 软链发布，保留 5 个版本；发布后自动做就绪探针
  与短链冒烟，失败自动回滚，人工回滚一条命令。
- 搭建 Prometheus + Alertmanager + Grafana，覆盖 7 个抓取任务、3 个规则文件共
  28 条告警，关键告警 1 分钟内送达 webhook；按 critical/warning 分组并配置抑制
  规则，降低衍生告警噪音。
- 实现 MySQL 每日备份 + 每周恢复演练（gzip/完整性/大小三重校验，7 天日备 +
  4 周周备）；20+ 项巡检每 5 分钟执行，6 个故障演练覆盖 CPU/磁盘/MySQL/应用/Redis/网络。
```

这 4 条分别对应：环境与部署、发布与回滚、监控与告警、数据与日常运维。面试官扫一眼就能看出你不是只装了一个服务。

### 写法 B：稍详细版（6 条）

适合项目栏能放 8～10 行，或者网申系统要求展开写。

```text
- 系统基线：Ubuntu 22.04 + VMware NAT，完成阿里云 apt 换源、ops 用户与精细化
  sudoers、sysctl/文件句柄调优、2G swap、SSH 密钥登录、ufw 与 fail2ban。
- 中间件：MySQL 8 仅监听 127.0.0.1，按 6GB 内存设置 buffer pool 与 max_connections，
  开启 1 秒慢查询；Redis 设 requirepass、maxmemory 256mb、allkeys-lru，禁用
  FLUSHALL/CONFIG；应用账号只给业务库 DML 权限。
- 应用与接入：FastAPI 短链服务由 gunicorn + systemd 托管，提供 live/ready 探针和
  Prometheus 指标；Nginx 做 80→443、自签 SAN 证书、JSON 访问日志、20r/s 限流，
  /metrics 仅内网可访问。
- 监控告警：Prometheus 2.53 + Alertmanager 0.27 + Grafana 9.5.21，7 个抓取任务，
  host/app/meta 三类规则共 28 条；配置 for、group_wait、repeat_interval 和
  HostDown/AppDown 抑制规则。
- 发布回滚：releases/<时间戳> + current 软链，发布后校验 /health/ready 并做真实
  短链冒烟，失败自动切回上一版；systemd TimeoutStopSec=35 保证优雅退出。
- 数据与日常：mysqldump --single-transaction 每日备份，gzip -t + 检查
  "Dump completed" + 大小校验；每周恢复演练比对行数；20+ 项巡检每 5 分钟跑一次，
  每日 08:00 生成巡检日报（服务/目标/告警/24h 请求与 5xx/P95/缓存命中率/备份/证书一页看完），
  备份/巡检/日报结果都写 textfile 指标；GitHub Actions 跑 ruff、bash -n、shellcheck、
  pytest、promtool。
```

### 写法 C：技能栏怎么写

只写真正动手做过的，不写“精通”，也不要把“知道概念”写成“熟练使用”。

```text
Linux：Ubuntu 22.04 日常运维；systemd、ufw、SSH、日志、进程/端口/磁盘排查
Shell：Bash 部署、巡检、备份、发布脚本；bash -n、shellcheck
Nginx：反向代理、HTTPS、限流、JSON 访问日志、stub_status
MySQL：安装与最小权限、慢查询、连接数、mysqldump 备份与恢复演练
Redis：密码与内存上限、allkeys-lru、缓存降级
监控：Prometheus / Alertmanager / Grafana，PromQL、告警规则、textfile collector
Git / CI：Git 分支与发布，GitHub Actions（ruff、shellcheck、pytest、promtool）
Python：FastAPI 短链服务维护、pytest 基础
```

不要把 Docker、K8s、Terraform、Ansible、云平台、Jenkins 写进技能栏。不是你永远不学，而是现在没有真实使用经验，写上去就是给自己挖坑。被问到时的诚实说法：

> “这个项目我刻意用传统方式打基础，想先把 systemd、端口、日志、权限这些底层练熟。容器和编排是我下一步计划，目前没有生产使用经验，我不敢说会。”

## 二、30 秒自我介绍

中文口语稿，约 190 字，正常语速 30～35 秒。不要背得像朗诵，宁可慢一点。

> 面试官您好，我叫wudiliackerman-007，大三，自动化/电子信息方向，Python 比较熟。这一个月我在 VMware 的 Ubuntu 上从裸机搭了一套单机运维环境：Nginx 反代 FastAPI，MySQL 加 Redis，Prometheus、Alertmanager、Grafana 做监控，发布、回滚、备份、巡检都脚本化。我还做了 28 条告警和 6 个故障演练，能讲清楚一次故障从告警到恢复的过程。我没有生产经验，但 Linux 排障是我愿意长期投入的方向，希望有机会从运维实习做起。

如果现场要求更短，删掉“MySQL 加 Redis”和“6 个故障演练”这两句，保留“单机环境 + 发布回滚 + 监控告警 + 愿意做 Linux”四个信息点。

## 三、项目讲解 3 分钟版

### 0:00–0:30 为什么做

> 我投的是 Linux/云计算运维实习，发现很多教程只教“把服务装起来”，但真实运维还要面对发布、回滚、告警、备份和故障。我就用 VMware 装了一台 Ubuntu 22.04，6GB 内存、4 核，故意不用容器，把从裸机到可运维的整条链路走一遍。项目叫 linux-ops-platform，业务是一个很小的 FastAPI 短链服务，重点不在业务，而在它周围的运维体系。

### 0:30–1:10 架构

> 用户访问先到 Nginx 的 80，301 跳到 443，证书是带 SAN 的自签证书；Nginx 反代到 127.0.0.1:8000 的 gunicorn，应用后面是 MySQL 8 和 Redis。Redis 只做缓存，挂了会自动回源 MySQL，并通过 opslink_dependency_up 暴露降级状态。监控是 Prometheus 每 15 秒拉 7 个目标，Alertmanager 做分组和抑制，Grafana 展示；所有 exporter 和数据库都只监听本地，不给公网。

### 1:10–2:30 我做的 3 个难点

> 第一个是发布和回滚。我没有用 scp 覆盖代码，而是每次发到 releases/<时间戳>，current 是软链；发布后先等 /health/ready，再真的创建一条短链验证 302，失败就自动切回上一版。回滚就是一条 ln -sfn 加重启，旧版本保留 5 个，线上跑的是哪个 commit 看 RELEASE 文件就知道。
>
> 第二个是监控不变成噪音。指标 label 我用的是 request.scope["route"].path，不是真实 URL，否则每来一个短码就多一条时间序列，几千条短链就能把 Prometheus 撑爆。规则按 host/app/meta 三个文件组织，共 28 条；条件都带 for，Alertmanager 里 HostDown 抑制同实例 warning，AppDown 抑制错误率，critical 和 warning 的发送节奏也分开。
>
> 第三个是备份要能证明可恢复。mysqldump 用 --single-transaction 导出，gzip 后做 gzip -t、检查 "Dump completed"、再校验大小；结果写进 node_exporter 的 textfile 指标，超过 48 小时没成功就告警。每周日还会把最新备份真正恢复到临时库，比对行数再删掉。备份不是“文件生成了”，是“恢复得出来”。

### 2:30–3:00 结果和边界

> 现在这套环境可以一条命令从裸机重建，20+ 项巡检每 5 分钟跑一次，6 个故障演练覆盖 CPU、磁盘、MySQL、应用、Redis 和网络，CI 里跑 ruff、bash -n、shellcheck、pytest 和 promtool。它让我能把一次故障从告警、定位、止血到复盘讲完整。边界也很清楚：单机、没有高可用，告警只到 webhook，没有做过真正的灰度和规模压测，这些是我下一步要补的。

## 四、8 个高频追问的应答

### 1. “这项目是你自己做的吗？”

**答法**：是，代码和脚本都在 Git 里，CI 能跑绿。业务 FastAPI 是我写的，运维脚本是我按官方文档和社区最佳实践一点点改的，不是照抄一个成品。我能现场解释 `release.sh` 里为什么先记录 `PREV`、为什么健康检查之后还要做一次真实短链冒烟，也能解释指标 label 为什么用路由模板而不是真实路径。参考过什么是正常的，但我能对自己的设计负责。

**注意**：不要把所有东西都说成“100% 原创”。用了 Ubuntu、Nginx、Prometheus 这些开源软件不丢人，丢人的是把别人的东西说成自己写的。

### 2. “有没有上过生产？”

**答法**：没有，只在 VMware 的单机实验环境里跑过。所以我不会说高可用、百万 QPS 或者“支撑了多少用户”。它的价值是把生产里常见的流程和故障做成可复现：发布失败怎么回、备份怎么验、Redis 挂了业务怎么降级。如果真上生产，至少还要补多机和高可用、异地备份、真实告警渠道、变更审批、安全加固和压测，这些我都清楚。

**注意**：承认没上过生产不掉分，硬编“我们生产环境”才会被追问到崩。

### 3. “为什么不用 Docker/K8s？”

**答法**：两个原因。一是国内网络拉镜像不稳定，我这个环境经常卡在拉取上；二是这个项目的目的就是练手工装、systemd、端口、日志、权限这些底层能力，容器会把很多细节藏起来。我不是排斥容器，Docker 和 K8s 是我下一步计划，但目前没有生产使用经验，所以简历里不写。真要用，我会先把镜像、网络、存储和编排的基本问题搞明白再上手。

**注意**：不要为了显得“潮”硬说会用 K8s；面试官问两个 YAML 细节就露馅了。

### 4. “遇到最难的问题是什么？”

**答法**：最难的不是装服务，是指标高基数。我一开始用真实 URL 做 label，后来意识到每来一个短码就会多一条时间序列，几千条短链就能把 Prometheus 撑爆。我改成 `request.scope["route"].path`，让 `/abc123` 归到 `/{code}`，并在 pytest 里加了断言，防止以后改回去。这件事让我理解 label 不是随便加的，监控设计本身也会制造故障。另一个是备份恢复，`mysqldump --databases` 生成的 dump 里带库名，恢复到临时库要先用 sed 替换，否则会覆盖生产库，这个细节我印象很深。

**注意**：讲一个具体的技术细节，比说“加班解决了”有说服力；不要编一个自己没做过的线上事故。

### 5. “如果 QPS 涨 10 倍怎么办？”

**答法**：先压测确认瓶颈，不先调参数。入口看 Nginx 的连接数、限流和 upstream 延迟；应用看 gunicorn worker、连接池和 P95；数据库看慢查询、索引、连接数和锁；Redis 看命中率和内存淘汰。单机 4 核 6GB 肯定扛不住 10 倍，所以我会先加一台应用机，用 Nginx upstream 分流，数据库先做读优化，再考虑主从；同时把监控和告警阈值跟着调整。这个项目目前没有做规模压测和高可用，这是我下一步要补的，我不会假装它已经能扛。

**注意**：不要一上来就说“加机器/上云”；先讲定位和分层，才像运维。

### 6. “怎么保证备份可用？”

**答法**：备份脚本不是导出完就结束：先检查 MySQL 可连接、备份目录剩余空间，再用 `--single-transaction` 导出，gzip 后做 `gzip -t`、检查文件里有 `Dump completed`、校验大小；任何一步失败都把状态写 0，并触发告警。每周日 `restore_test.sh` 会把最新备份真正恢复到 `opslink_restore_check`，比对 `links` 行数，再删临时库。现在 RPO 最多 24 小时，RTO 对这个库是分钟级；不足是备份和数据库同机、没有异地、没有 binlog 时间点恢复，这些是下一步。

**注意**：不要只说“我每天备份”；要说“我怎么验证它能恢复”。

### 7. “告警太多怎么办？”

**答法**：先删掉不可行动的告警，再做分组和抑制。项目里 28 条规则按 critical/warning 分级，条件都带 `for`，比如 CPU 持续 5 分钟、磁盘 10 分钟；Alertmanager 的 `group_wait` critical 10 秒、warning 2 分钟，`repeat_interval` 1 小时/6 小时；`HostDown` 抑制同实例 warning，`AppDown` 抑制错误率。维护窗口用 silence，不直接关规则。现在告警只到 webhook，没有值班轮换和电话通知，这是局限；下一步会接真实渠道并做分级。

**注意**：降噪不等于把告警关掉；要说清楚“哪些该报、哪些不该报”。

### 8. “你觉得这个项目还有什么不足？”

**答法**：第一，单机没有高可用，Prometheus、MySQL、应用都是单点；第二，备份在本地，没有异地和 PITR；第三，告警只到 webhook，没有真实值班渠道；第四，没有做真正的灰度发布和规模压测；第五，监控和 Grafana 在实验环境里对局域网开放，生产要收紧。优先级我会先补高可用和异地备份，再补告警渠道和灰度。这个项目是“流程完整”，不是“生产规模”，我知道边界在哪。

**注意**：说不足要具体，不要用“还不够完善”这种空话；每一条最好带一个改进方向。

## 五、不要说的话

### 1. 不要把“搭过实验环境”说成“运维过生产”

**为什么**：面试官追问一句“你们生产多少台、用的什么负载均衡、出过什么事故”就会露馅。  
**改成**：“我在 VMware 单机上把流程跑通了，生产规模和高可用还没做过，这是我下一步要补的。”

### 2. 不要堆没做过的名词

**为什么**：K8s、Docker、Terraform、云平台这些词，写上去就要经得起追问；没做过就是没做过。  
**改成**：“这个项目刻意用传统方式打基础，容器和编排是我下一步计划，目前没有生产经验。”

### 3. 不要把教程或开源项目说成完全自研

**为什么**：用开源软件很正常，把别人的设计说成自己原创，反而显得不诚实。  
**改成**：“我参考了官方文档和社区的最佳实践，业务和脚本是我自己写和改的，我能解释每个关键设计为什么这么做。”

### 4. 不要说“监控告警全自动，不用人管”

**为什么**：告警需要响应、抑制、复盘和调阈值；说“不用人管”会让面试官觉得你没做过 on-call。  
**改成**：“告警负责发现问题，人负责判断影响和止血；我做了分组、抑制和 for，尽量减少噪音，但不能替代值班。”

### 5. 不要回避“单机、没高可用”

**为什么**：这是项目最大的边界，越躲越显得心虚；主动讲清楚，反而说明你知道生产还差什么。  
**改成**：“它是单机实验环境，优势是流程完整、可复现；生产要补多机、高可用、异地备份和真实告警渠道。”

## 六、面试前 10 分钟快速检查

- 30 秒自我介绍能不能不看稿说完？
- 能不能在白纸上画出“用户 → Nginx → gunicorn → MySQL/Redis + Prometheus/Alertmanager/Grafana”？
- 能不能说出 3 个数字：28 条告警、20+ 项巡检、6 个故障演练？
- 能不能解释一次发布失败自动回滚的完整顺序？
- 有没有准备好一句诚实的“我没做过生产，但我知道差什么”？
