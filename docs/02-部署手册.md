# 02 部署手册

> 两种走法：想快 → `sudo ./deploy/all_in_one.sh`；想懂 → 按本文档一步一步来。
> 两者跑的是同一批脚本，分步执行只是把 `all_in_one.sh` 的六步拆开，方便中途看日志、拍快照。
>
> **读者**：要在这台机器上真正部署、或者要判断「装到哪一步了、出问题会是什么现象」的人。
> **完成后得到**：8 个服务全部 active、7/7 抓取目标 up、巡检 20/20 通过。

## 0. 前置条件

- Ubuntu 22.04，root 权限，能访问 `mirrors.aliyun.com`、`mirrors.tuna.tsinghua.edu.cn` 和 `gh-proxy.com`（GitHub 下载加速；脚本里已写死多候选地址，一个不通会自动换下一个）
- 已配好免密 SSH（见 `01-环境准备.md` 第 5 节）
- 仓库已在 `/opt/ops-platform/repo`
- 建议先拍快照 `before-deploy`

```bash
cd /opt/ops-platform/repo
ls deploy/          # 应看到 bootstrap.sh install_*.sh all_in_one.sh lib/
```

## 1. 系统初始化 `bootstrap.sh`

```bash
sudo ./deploy/bootstrap.sh
```

做了这些事：

| 类别 | 内容 |
|------|------|
| 换源 | `/etc/apt/sources.list` → 阿里云；`apt update && upgrade` |
| 基础包 | curl vim git htop iotop sysstat jq unzip net-tools chrony ufw fail2ban logrotate rsync ufw python3-venv build-essential libmysqlclient-dev |
| 时间 | `timedatectl set-timezone Asia/Shanghai`，chrony 校时 |
| 用户 | 创建 `ops`（无 sudo ALL，写精细化 `/etc/sudoers.d/ops-platform`） |
| 目录 | `/opt/ops-platform/{releases,shared,current,bin}`、`/data/{mysql,backup,chaos}`、`/etc/ops-platform`、`/var/log/ops-platform`，属主 `ops` |
| 内核 | `/etc/sysctl.d/99-ops.conf`：`somaxconn=1024`、`tcp_tw_reuse=1`、`vm.swappiness=10`、`fs.file-max`、`ip_local_port_range` |
| 资源 | `nofile 65535`（`/etc/security/limits.d/99-ops.conf`）、2 GB swap 文件 |
| 安全 | ufw 默认拒绝入站、放行 22/80/443/3000/9090/9093；fail2ban 监控 sshd；**仅当 `~ops/.ssh/authorized_keys` 存在**才 `PasswordAuthentication no` |
| 密钥 | 生成 `MYSQL_ROOT_PASSWORD`、`MYSQL_APP_PASSWORD`、`REDIS_PASSWORD`、`GRAFANA_ADMIN_PASSWORD` 写入 `/etc/ops-platform/platform.env`(600) |

**验证：**

```bash
source /etc/ops-platform/platform.env && echo "root pw 长度=${#MYSQL_ROOT_PASSWORD}"
sudo -l -U ops                 # 应只列出少数命令，不能 ALL
swapon --show                  # 应有 2G
sysctl net.core.somaxconn      # 1024
sudo ufw status verbose
```

## 2. 中间件 `install_middleware.sh`

```bash
sudo ./deploy/install_middleware.sh
```

- MySQL 8：`bind-address=127.0.0.1`，`innodb_buffer_pool_size` 按内存 40% 推算（6 GB → 约 1.2 GB），
  开慢查询日志（`long_query_time=1`），建库 `opslink` + 表（`app/schema.sql`）
- 账号：`opslink@127.0.0.1`（只对 `opslink.*` 有 DML）、`exporter@127.0.0.1`（只 `PROCESS, REPLICATION CLIENT`）
- `/root/.my.cnf`（600）：后续所有脚本免密执行 mysql，**不再在命令行里传密码**
- Redis 6.0（Ubuntu 22.04 官方源版本）：`requirepass`、`maxmemory 256mb`、`maxmemory-policy allkeys-lru`、禁用 `FLUSHALL`/`CONFIG`/`KEYS`
- 写 `/etc/ops-platform/app.env`（应用的连接信息，600）

**验证：**

```bash
sudo mysql --defaults-file=/root/.my.cnf -e "SHOW DATABASES; SELECT user,host FROM mysql.user;"
mysql -h127.0.0.1 -uopslink -p"$(grep ^MYSQL_APP_PASSWORD= /etc/ops-platform/platform.env | cut -d= -f2)" -D opslink -e "DESC links;"
redis-cli -a "$REDIS_PASSWORD" --no-auth-warning ping     # PONG
sudo ss -lntp | grep -E '3306|6379'                       # 都应是 127.0.0.1
```

> 拍快照 `after-middleware`。这是最值得回滚的一个点。

## 3. 业务应用 `install_app.sh`

```bash
sudo ./deploy/install_app.sh
```

- 共享 venv `/opt/ops-platform/venv`（pip 用清华源）
- 新版本目录 `releases/<时间戳>`，rsync 代码（排除 tests）
- `opslink.service`：`Type=simple`、`User=ops`、`EnvironmentFile=/etc/ops-platform/app.env`、
  `ExecStart=venv/bin/gunicorn --config current/app/gunicorn.conf.py`、
  `NoNewPrivileges=yes`、`ProtectSystem=strict`、`ReadWritePaths=/var/log/ops-platform`、`Restart=always`、`RestartSec=3`
- 切软链 `current -> releases/<ts>`，然后冒烟：建短链 → 取 code → 校验 302

**验证：**

```bash
curl -s http://127.0.0.1:8000/health/live; echo
curl -s http://127.0.0.1:8000/health/ready; echo
CODE=$(curl -s -X POST http://127.0.0.1:8000/api/shorten -H 'Content-Type: application/json' -d '{"url":"https://example.com"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["code"])')
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' http://127.0.0.1:8000/$CODE
curl -s http://127.0.0.1:8000/metrics | grep -E 'opslink_dependency_up|opslink_links_created_total'
```

## 4. Nginx `install_nginx.sh`

```bash
sudo ./deploy/install_nginx.sh
```

- 自签证书 `/etc/ssl/opslink/opslink.crt`（SAN=本机 IP + localhost，365 天）
- `sites-available/opslink.conf`：80→301、443 TLS1.2/1.3 http2、安全响应头、
  `limit_req_zone 20r/s` + `limit_conn 50`、`/api/` burst=40 nodelay 返回 429、
  `/metrics` 仅内网、`/stub_status` 在 `127.0.0.1:8081`、JSON 日志 `ops_json`
- 删掉 default 站点，`nginx -t` 通过才 reload

**验证：**

```bash
curl -sI http://<IP>/ | head -3                       # 301 → https
curl -sk https://<IP>/health/live; echo               # ok
curl -s http://127.0.0.1:8081/stub_status | head -4   # Active connections
sudo tail -2 /var/log/nginx/opslink_access.log        # 应是 JSON 一行
sudo nginx -t
```

## 5. 监控 `install_monitoring.sh`

```bash
sudo ./deploy/install_monitoring.sh
```

- 5 个二进制走 `gh-proxy.com` 代理 GitHub Releases（华为云做后备），装到 `/usr/local/bin`；Grafana 用清华镜像的 deb。`download()` 会校验内容：镜像返回 HTML 错误页或非 gzip 文件都算下载失败，自动换下一个地址
- 注意 nginxinc 的 exporter 包内**没有顶层目录**（二进制直接在根），脚本对这种情况单独处理
- 渲染 `prometheus.yml`（把 `__INSTANCE_IP__` 换成本机 IP）和 `alertmanager.yml`（`__WEBHOOK_URL__` → `http://127.0.0.1:5001/webhook`）
- **上线前校验**：`promtool check config`、`promtool check rules`、`amtool check-config`，不通过就退出
- 6 个 systemd 服务：prometheus / alertmanager / node_exporter / mysqld_exporter / nginx-prometheus-exporter / alarm-receiver
- Grafana：数据源 + 看板通过 provisioning 自动加载（`/etc/grafana/provisioning/`）

**验证：**

```bash
curl -s http://127.0.0.1:9090/-/ready
curl -s http://127.0.0.1:9090/api/v1/targets?state=active \
  | python3 -c 'import sys,json;[print(t["labels"]["job"],t["health"]) for t in json.load(sys.stdin)["data"]["activeTargets"]]'
# 期望 7 行全部 up
curl -s http://127.0.0.1:9100/metrics | head -3
curl -s http://127.0.0.1:9113/metrics | grep nginx_connections_active
curl -s http://127.0.0.1:5001/healthz
```

Grafana 密码：

```bash
grep GRAFANA_ADMIN_PASSWORD /etc/ops-platform/platform.env
```

## 6. 定时任务 `install_timers.sh`

```bash
sudo ./scripts/install_timers.sh
sudo systemctl list-timers 'ops-*'
```

| Timer | 频率 | 做什么 |
|-------|------|--------|
| `ops-backup.timer` | 每天 03:20（±5 分钟随机） | `backup_mysql.sh`：dump + 校验 + 写指标 |
| `ops-healthcheck.timer` | 开机 2 分钟后，之后每 5 分钟 | `healthcheck.sh -q`：20+ 项巡检 |
| `ops-report.timer` | 每天 08:00（±2 分钟随机） | `daily_report.sh`：生成当日巡检日报 |
| `ops-restore-test.timer` | 每周日 04:30 | `restore_test.sh`：恢复最新备份到临时库比对行数 |

巡检和日报的分工（常被问"既然有监控为什么还要这两个"）：

- 监控（Prometheus）负责**趋势和告警**，是被动的；
- 巡检（5 分钟）负责**"现在到底能不能用"**，是主动的端到端拨测，包含监控自己有没有挂；
- 日报（08:00）负责**"昨天一天过得怎么样"**，把主机/服务/告警/应用指标/备份/证书拼成一页，
  值班交接和早会直接看它，不用登录机器逐个命令敲。

先手动跑一次，确认不是"定时器装了但脚本是坏的"：

```bash
sudo systemctl start ops-backup.service
sudo journalctl -u ops-backup -n 30 --no-pager
sudo /opt/ops-platform/bin/healthcheck.sh
sudo systemctl start ops-report.service && sudo cat /var/log/ops-platform/report/latest.txt
```

## 9. 常见报错

| 报错 | 原因 | 处理 |
|------|------|------|
| `apt-get update` 报 `NO_PUBKEY` | 换源后缺 key | `apt-key adv` 或直接删掉第三方 list，只留 main/universe |
| `mysql: command not found` | MySQL 未装完 | `apt-get install -y mysql-server`，看 `/var/log/mysql/error.log` |
| `Access denied for user 'opslink'` | 账号 host 限定 127.0.0.1 而用了 localhost/socket | 用 `-h127.0.0.1`；或检查 `app.env` 里 host |
| `redis: NOAUTH Authentication required` | 没带密码 | `redis-cli -a "$REDIS_PASSWORD" --no-auth-warning` |
| systemd 起不来，`status=203/EXEC` | ExecStart 路径不对/无执行权 | `ls -l` 看 `current` 软链是否断、venv 是否存在 |
| `status=209/STDOUT` | 单元里用了 `>` 重定向 | 重定向要写 `StandardOutput=append:/path`，不能写在 ExecStart |
| 502 Bad Gateway | 应用没起 / 端口不对 | `journalctl -u opslink -n 50`、`ss -lntp \| grep 8000` |
| Prometheus target `connection refused` | exporter 监听 127.0.0.1 但配置写了外网 IP | 配置里统一用 `127.0.0.1` |
| Grafana 登录失败 | 改了 ini 但没重启 / 已存在 admin 用户 | `systemctl restart grafana-server`，必要时 `grafana-cli admin reset-admin-password` |
| `promtool` 报 YAML 语法错 | 规则里出现中文直引号 `"..."` | 用单引号或 `「」`，见 `rules/app.yml` |
| 时间不对导致告警时间乱 | 时区/chrony | `timedatectl set-timezone Asia/Shanghai && systemctl restart chrony` |

## 10. 重装 / 清理

三个不同量级的操作，从轻到重：

```bash
# 1) 只回滚代码，不动数据
sudo ./scripts/rollback.sh                 # 回上一个「好」版本（自动跳过发布失败留下的 BROKEN 版本）
sudo ./scripts/rollback.sh --list          # 看有哪些版本，坏版本会标出来
sudo ./scripts/rollback.sh --force 20250101120000   # 明知是坏版本也要回去（几乎不该用）

# 2) 拆掉平台但保留数据（重装的正确姿势，1 分钟装回来）
sudo ./deploy/cleanup.sh --dry-run         # 先看它准备做什么
sudo ./deploy/cleanup.sh                   # 停服务、卸 systemd 单元、撤站点，数据/密钥/备份全留
sudo ./deploy/all_in_one.sh                # 装回来，密码不变、数据还在

# 3) 彻底清空（会删数据和密钥，不可恢复）
sudo ./deploy/cleanup.sh --purge

# 连 apt 装的中间件一起删
sudo apt-get purge -y mysql-server redis-server nginx grafana
```

`cleanup.sh` 默认**不删数据**是刻意的：用户说「重装一下」时，九成只是想重跑一遍部署脚本，
而 `all_in_one.sh` 本来就是幂等的（见 `docs/05` 第 6 节）。真删数据必须显式加 `--purge`。

清理脚本的实测结果（跑完残留进程 0 个、443 连不上、数据都在、再装回来 20/20 全绿）记在
`docs/05-实机验证报告.md` 第 8 节。

发布/回滚的实测数据（坏版本 34 秒自动回滚、好版本 1～2 秒、手动回滚 2 秒、坏版本被拒绝回滚）
记在 `docs/05-实机验证报告.md` 第 10 节。
