# 00 项目概述与架构

> 这份文档回答三个问题：这个项目是什么、为什么这么设计、数据怎么流动。
> 需要讲清楚架构时，画这一页就够了。
>
> **读者**：第一次接触本项目、想先看全貌的人。**用时**：10 分钟。
> **读完能**：画出架构图、说清每个组件的职责与端口、解释 8 条设计取舍。

## 一句话

在一台 Ubuntu 22.04 上，用**可重复执行的脚本**搭出「应用 + 数据库 + 缓存 + 反向代理 + 监控告警 + 发布回滚 + 备份巡检」的完整环境，并配套 6 类故障演练。

## 为什么选这个形态

最初考虑过用 Docker Compose 起一套，评估后放弃：

1. 国内拉不到 Docker Hub 镜像，实习现场/学校网络同样拉不到，**换台机器就跑不起来**；
2. 运维工作里最常考的往往是「进程为什么没起来」「磁盘为什么满了」「502 到底是哪一层」，这些能力在手工环境里练得更扎实；
3. 单机 + Shell 脚本能**完全复现**，仓库里 60% 是配置文件和脚本，clone 下来就能重建。

所以项目定位很明确：**传统 Linux 运维的完整闭环，不是云原生**。K8s / 容器在文档里只作为"下一步"出现。

## 组件与端口

| 组件 | 版本 | 监听 | 作用 | 配置文件 |
|------|------|------|------|---------|
| Nginx | 1.18 | `0.0.0.0:80,443`、`127.0.0.1:8081` | 入口、TLS、限流、访问日志 | `/etc/nginx/sites-available/opslink.conf` |
| opslink | 应用代码 | `127.0.0.1:8000` | 短链服务（gunicorn 多 worker） | `/opt/ops-platform/current/app/` |
| MySQL | 8.0 | `127.0.0.1:3306` | 短链持久化 | `/etc/mysql/mysql.conf.d/` |
| Redis | 7.0 | `127.0.0.1:6379` | 短码缓存，TTL 1h | `/etc/redis/ops.conf` |
| Prometheus | 2.53.0 | `0.0.0.0:9090` | 指标抓取 + 规则计算 | `/etc/prometheus/prometheus.yml` |
| Alertmanager | 0.27.0 | `0.0.0.0:9093` | 告警分组/抑制/路由 | `/etc/alertmanager/alertmanager.yml` |
| Grafana | 9.5.21 | `0.0.0.0:3000` | 可视化 | `/etc/grafana/grafana.ini` + provisioning |
| node_exporter | 1.8.2 | `127.0.0.1:9100` | 主机指标 + textfile 自定义指标 | systemd 参数 |
| mysqld_exporter | 0.15.1 | `127.0.0.1:9104` | MySQL 指标 | `/etc/mysqld_exporter/.my.cnf` |
| nginx-prometheus-exporter | 1.4.1 | `127.0.0.1:9113` | Nginx 连接数 | systemd 参数 |
| alarm-receiver | 自写 | `127.0.0.1:5001` | 接收 webhook、落日志 | `scripts/webhook_receiver.py` |

**端口安全原则**：所有 exporter、MySQL、Redis、应用都只监听 `127.0.0.1`；
对外的只有 80/443（业务）、9090（Prometheus，方便查看）、9093、3000（演示用，ufw 限制来源）。
真实生产会把 9090/3000 也收进内网或加认证 —— 这是本项目的已知简化。

## 请求链路

```
浏览器
  │ HTTPS 443
  ▼
Nginx ── limit_req(20r/s) ── 访问日志 opslink_access.log(JSON)
  │ proxy_pass 127.0.0.1:8000（keepalive 32）
  ▼
gunicorn/opslink
  │ 1. Redis GET code           命中 → 302（记 cache_hits）
  │ 2. 未命中 → MySQL SELECT     → 回写 Redis（记 cache_misses）
  │ 3. Redis 连不上 → 跳过缓存，直接 MySQL，并置 opslink_dependency_up{redis}=0
  ▼
返回 302 Location / 404
```

关键点：**缓存失败不阻断请求**。运维视角上，"降级"必须同时满足两件事 —— 业务还能用，且监控能看出来。

## 监控数据流

```
node_exporter / mysqld_exporter / nginx-exporter / opslink /prometheus
        ▲ 每 15s 拉取（pull 模型）
        │
   Prometheus ──每 15s──▶ 计算 /etc/prometheus/rules/*.yml
        │                        │ 规则变为 firing
        │                        ▼
        │                  Alertmanager（分组 30s / 抑制 / 去重）
        │                        │ webhook
        │                        ▼
        │                  alarm-receiver :5001 → /var/log/ops-platform/alerts.log
        ▼
     Grafana（数据源 provisioning，看板 JSON 自动加载）
```

为什么用 pull 而不是 push：目标挂了 Prometheus 立刻能从 `up==0` 发现；push 模式下"没数据"和"没上报"分不清。

## 发布模型

```
/opt/ops-platform/
├── releases/
│   ├── 20250101-101500/   旧版本
│   ├── 20250102-093000/   新版本  ← 每次发布一个新目录
│   └── ...
├── current -> releases/20250102-093000   ← 原子切换
└── venv/                                 ← 所有版本共享，依赖就地升级
```

`release.sh` 的步骤：拉代码 → 建 release 目录 → 同步依赖 → `ln -sfn` 切换 → `systemctl restart` →
轮询 `/health/ready` + 真实发一条短链 → 失败自动切回上一个 release 并重启。
回滚 = `ln -sfn` + restart，秒级完成，不依赖重新构建。

## 为什么是这些文件

| 目录 | 为什么单独拆出来 |
|------|-----------------|
| `deploy/lib/common.sh` | 常量（路径、端口、版本号）和函数（下载重试、apt、生成密钥、健康检查）集中一处，改端口只改一个文件 |
| `deploy/*.sh` | 每个脚本只做一件事，能单独重跑；`all_in_one.sh` 只是按顺序调用 |
| `monitoring/` | 监控配置和代码一起进 Git，规则变更走 PR + `promtool` 校验 + CI |
| `scripts/` | 日常运维动作（备份、巡检、发布）全部脚本化，人能做的机器也能做 |
| `ops/chaos/` | 故障演练脚本化，才能"每周练一次"而不是"想起来才做" |

## 已知取舍

- **单点**：Prometheus、MySQL、Grafana 都是单实例。做高可用需要主从 + 远端存储 + 负载均衡，超出 1 个月时间盒。
- **自签证书**：没有域名，用 `openssl` 自签（含 SAN），浏览器告警属预期；生产应接 ACME。
- **无压力测试**：只有 `ab`/`curl` 简单验证限流，没有做容量规划。
- **告警只到日志**：webhook 接收器写文件，没接企业微信/短信。接起来只要改 Alertmanager receiver，但需要真实 token。
